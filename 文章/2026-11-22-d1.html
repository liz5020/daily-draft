GitHub 專案管理新手系列（1）：Git 為什麼是專案管理的底座

很多人第一次用 AI 寫程式，會把所有檔案放在電腦的同一個資料夾，然後一直請 AI 修改。直到某一次畫面壞掉、功能消失，才發現自己不知道是哪一次改壞的、改了哪些檔案、要怎麼回到原本正常的版本。作者 @pmenance.manager 自稱軟體菜鳥 PM，他把半年前分享過的「用 GitHub 做專案管理」重新整理成系列，第一篇不教開看板，而是先講：為什麼第一步是版本控管。

版本控管，就像遊戲存檔

作者的比喻很直白：每完成一小段工作，就建立一個 Commit，它會留下三件事：什麼時候改的、改了哪些檔案、為什麼要改。之後發現功能壞掉，就能比較兩個版本差在哪裡，也能回到還正常的存檔點。這比自己複製出「最終版、最終版 2、真的最終版」可靠得多。

Git 負責記錄電腦裡的版本，GitHub 的 Repo（專案倉庫）則把這些版本放到線上。作者列了五個好處：

  1. 電腦故障或換電腦，程式與歷史都還在；
  2. 團隊與 AI 能讀到同一份專案；
  3. 新功能可以先在不同的分支（branch）修改；
  4. 合併前可以透過 PR（合併請求）檢查改了什麼；
  5. 不想公開的專案，可以建立 Private Repo。

為什麼這跟專案管理有關

專案管理不能只知道「做到哪裡」，還要追得到「為什麼改」和「實際改了什麼」。作者把各個零件的分工整理成一串：Commit 留下每一次實際修改；Repo 集中程式、版本與協作紀錄；Issue 記錄修改原因、需求與驗收條件；Project 追蹤優先度、負責人、進度與日期；Branch 與 PR 把修改隔離起來，交給人檢查後再合併。這些資料串起來之後，看板上的進度才會連到真正的開發成果，作者認為這才是 GitHub 專案管理最有價值的地方。

他舉的例子是「會員搜尋」：先在 Project 排好優先度，開 Issue 寫需求與驗收條件，從 Issue 建 branch 開始修改，每完成一段就留下 Commit，開 PR 說明改了什麼、測了什麼，人工驗收通過後再合併並完成 Issue。

對 AI 協作的意義

AI 可以從 Repo 讀目前的程式，從 Issue 讀需求與驗收條件，從 PR 看它改了什麼、跑了哪些測試。就算換聊天室、換另一個 AI，重要的脈絡仍然留在 GitHub。但作者強調，需求要不要做、驗收有沒有通過、能不能正式上線，仍然交給人決定。

第一步怎麼做

  1. 在電腦建立專案資料夾；
  2. 放入程式、README 與 .gitignore（列出不要上傳的檔案）；
  3. 請 AI 先檢查有沒有不該上傳的資料；
  4. 建立第一個 Commit；
  5. 建立 Private Repo 並推上去（Push）；
  6. 回到 GitHub 確認檔案與 Commit 都存在。

作者特別提醒第 6 步：AI 說「已完成」之後，還是要自己回 GitHub 看三個地方：預設分支與可見性是否正確、檔案與 README 是否出現、有沒有第一筆可追溯的 Commit。

分支怎麼規劃

分支用來區隔不同成熟度的版本：develop 是正在整合與測試的新功能，部署到開發測試站；release 是準備上線的候選版本，部署到 Staging 做最後驗收；main 或 master 是已確認可以正式使用的版本，部署到 Production。名稱可以依團隊調整，重點是每條分支的責任要固定。

  • feat 不是長期分支：通常一個功能開一條，例如 feat/member-search，完成後開 PR 合回 develop，整批驗證後晉升 release，最後驗收後再晉升 main。
  • Bug 與緊急修正：Bug 可依發現位置開 fix 分支；正式站需要立即修正時，才從正式版本開 hotfix，上線後要回併開發主線，避免下一次發布又把已修好的問題蓋回去。
  • 分支不等於環境：Branch 只是不同版本的程式碼，不會自己變成能開啟的網站；要讓 develop 自動到測試站、release 自動到 Staging，還需要 CI/CD（自動部署）設定規則。大型專案甚至替每個 feat 準備獨立的資料庫與預覽網址，讓多個功能同時測試、不互相覆蓋。
  • 小專案可以簡化：小型 side project 先用 develop 加 main 兩層就好，等真的有獨立驗收流程，再加入 release。

幾個提醒

  • 這是作者的個人教學，他自述是軟體菜鳥 PM；內容是通用的 Git 與 GitHub 工作流程（偏 Git Flow 風格），並非他獨創。
  • develop、release、main 三層適合較大的團隊，作者自己也說小專案可以只用兩層。
  • 具體的 GitHub 介面步驟，這裡沒有逐項核對，實作時以 GitHub 官方說明為準。
  • 下一篇預告：用 Issue Forms 把一句「幫我改一下」，整理成可以驗收的工作。

可以怎麼用

如果你有一個正在請 AI 修改的資料夾，今天先做第一步：建立第一個 Commit，把現在還正常的狀態存下來。之後 AI 改壞了，你至少有一個回得去的存檔點。
