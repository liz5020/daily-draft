約 3 分鐘　頭條　AI 協作與治理　舊文 11/07

Claude 文件 artifact 難讀：找報告撰寫方法做成 skill

有人覺得 Claude 做出來的文件 artifact「一坨」：字很多、框很多、很難讀。他想回頭找 AI 時代之前就成熟的報告寫法，轉成 skill 或 plugin。串裡最有意思的，是後面關於「報告到底該寫給人還是寫給 agent」的討論。

作者的痛點

  • 公司請他做 AI 報帳 bot，他自己試用很好用，但請 Claude 寫的教學文件反而讓人不知道怎麼用：只是把一堆字放在卡片裡，沒有合適的排版，用字也怪怪的。
  • 平常開發要盤點進度、寫系統設計，artifact 總是只會三招：增加字、減少字、把字框起來，沒法吸收和閱讀。
  • 他想要的報告：有適當的圖表與精練的資訊，能加速主事者的決策。Codex 也差不多。
  • 試過的辦法：把 ASD-STE100 放進輸出風格、提示詞加上「可視化」，效果有限，還要一直來回調整；花太多時間在報告上本末倒置。

他的想法與留言的建議

作者想找 AI 時代前成熟的報告撰寫方法，做成 skill（目前還沒找到，說有結果會分享）。ASD-STE100 是真實存在的受控英語規格，源自航太業，Issue 9 在 2025 年 1 月發布，主要目的是讓用字單一、不產生歧義。

@peter_career_hack 建議：請 AI 站在 UAT（使用者驗收測試）的角度，列出使用者會卡關的點，再用 playwright 模擬操作路徑，做出圖文並茂的使用手冊。他同時預測：幾個月後 agent 對 agent 的時代，要思考的是怎麼把資訊整理成適合 agent 讀的結構，資訊量大到人看不完，這些說明書也會被丟掉。

作者的兩個追問

  1. 什麼是適合 agent 讀的資訊？他的看法是底層其實還是常見的網路協定加 JSON，再配上 agent 需要的 metadata，暫時不會有大變化（他也說可能是自己了解得不夠深，歡迎補充）。
  2. 說明書會被丟掉，但人不可能不看 agent 的報告。資訊要濃縮到什麼程度、談多高的層次，人與 agent 才能對齊？就像老闆要看高管的報告、高管要跟主管開會、主管要跟團隊一起工作。他的體感是：現在最前沿的模型還在「主管」等級，但這取決於 harness 的設計、模型能力、上下文記憶大小與投入的成本。

跟知識庫怎麼接

  • AI 使用整理把它跟「去 AI 味」放在一起：那一則處理文字的口氣，這則處理排版與資訊層次。
  • 做成 skill 的方法，見 AI 規則與 Skill 整理的第 5 步（流程做成 skill），以及「用 Skill 取代 Prompt」那篇。
  • 你自己的知識庫已經有答案雛形：「網頁與簡報製作規範」與這個電子報站台，都規定了文章骨架（導言、圖解、重點、怎麼用、備註）和字數，這就是把「好讀」寫成規則。
  • 版面與圖形說理的框架，見設計與簡報整理。

可以怎麼用

下次請 AI 寫報告前，先告訴它三件事：給誰看、讀完要做什麼決定、他有幾分鐘；並要求第一句就是結論、重點不超過三個。做了幾次之後，把這個格式存成 skill。

來源與備註：Threads @azetry0422，2026-11-07，含留言討論。作者與留言者都是分享個人經驗與預測，沒有註明背景；ASD-STE100 的規格為真實存在。

給 Claude Code 的指令

適合情境：覺得 AI 做的報告字多、框多、很難讀，想讓它改成好讀的格式時

請先讀懂下面的需求，列出你打算讀哪些檔案、改哪些地方、步驟是什麼，等我說「好」再動手；不要直接修改或刪除任何檔案。

請幫我設計一個「好讀報告」的做法，讓你以後寫報告都照做。步驟：1. 先問我三件事：報告給誰看、他要做什麼決定、他能花幾分鐘讀。2. 依答案擬一份固定格式：第一句結論、三個以內的重點、必要的圖表（說明什麼情況該用表格或圖）、風險與下一步，並規定字數上限與不要把字框起來湊版面。3. 把這份格式寫成 skill 草稿（SKILL.md 的內容），貼給我看。4. 用我最近一份報告當範例，示範改寫前後的差別。我說「好」才建立 skill 檔案。

貼進 Claude Code 後，它會先列出要改什麼、等你說「好」才動手。同一份指令也存在原筆記的「給 AI 的指令」。
